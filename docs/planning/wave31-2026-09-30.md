## §S — Server play and client match state (P10, spectator, P3 names, P18)

Order of tasks, most important first.

1. **P10 (found) — a reload with a SELECTION open is a soft-lock.** An open *ask*
   is already re-sent and covered end to end (`e2e/play.spec.ts`, the refresh
   block). A *selection* is not: `Match.resendAfterSnapshot`
   (`apps/server/src/play/match.ts:620`) re-sends says, prompt, buttons, asks and
   `ended`, and nothing else; and the client's `applySnapshot`
   (`apps/ui/src/play/live/match.ts:1437`) nulls `selectables`, `weaklySelectable`
   and `highlighted` on the premise that *"the server does NOT re-send"* them.
   So a decision that is a selection (the London bottom pick, a target, a payment)
   is dead after a reload, with Forge waiting.
   - Keep each seat's current selection, highlight and actionable set on the server,
     and re-send them in `resendAfterSnapshot`. Fix the client comment and its
     tests, which state the opposite.
   - Test against real Forge: open a selection, drop the socket, rejoin, and assert
     the seat receives the same selectables. **Reverted fails, restored passes, with
     counts.** (E adds the browser-level reload; yours is the socket-level proof.)
2. **Spectator.** Today nothing stops it: `apps/server/src/play/socket.ts` gates
   `clientToServer`, `fullControl` and `stopPreference` only on `joined.get(match.id)`,
   and `match.claim` hands a returning participant its seat. On the real match
   `m-4c9483b3ec01`, seat 0 was `joined` at 19:41:25 by a second browser while the
   first was still connected. Design, checked against the code:
   - Viewing needs no change: frames already reach every socket in the seat's room,
     and it is the same person's own hand.
   - **One controlling socket per seat.** The first connection to claim a seat
     controls it. A later connection for the same seat while the controller is
     connected joins as a **spectator**: the server refuses its three inputs and logs
     `c2s-spectator`. The server enforces; the UI only explains (shape 3).
   - **Promotion on disconnect.** When the controller leaves, the longest-connected
     spectator for that seat becomes the controller, gets its asks re-sent
     (`resendAfterSnapshot`), and is told on `forge:role`.
   - **A refresh is this same path and must be a test.** A refresh can open the new
     socket before the old one's `disconnect` lands (why `disconnectGraceMs`
     exists), so the refreshed tab spectates for a moment and is then promoted. A
     refresh must never leave a player locked out of their own seat.
   - Tests: refused inputs; promotion; the refresh race (new socket joins before the
     old one leaves); a spectator whose controller never leaves stays refused.
     Mutation counts for each guard.
3. **P3 names (found).** *"instead of 'seat 1/seat 2' should show names"*: the names
   are `Seat 1` / `Seat 2` because `socket.ts:295,300` hardcodes them as the Forge
   players' names. Accept `names` (shape 1) and use it as the Forge player name, so
