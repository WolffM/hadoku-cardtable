## Settled — do not re-open

- **The CI signal is the deliverable.** "Done" for this wave is `forge-e2e` green on main, not a local
  green. A local loop that passes proves nothing about a CI-only race until it has been made to FAIL
  locally first (see §A.1).
- **Scenarios are e2e/jvm-only machinery.** Never change product behaviour to make a scenario start.
  A fix that touches a no-scenario code path is out of scope; stop and report.
- **No retries, no longer timeouts.** Playwright `retries: 0` stays. A precondition timeout raised from
  N to 2N is not a fix and will not be accepted.
- CI queues instead of cancelling (`5a4cae0`). Don't change `.github/workflows/ci.yml` this wave.

## §A — Scenario start, in the bridge (the long pole)

The first priority window after a scenario applies must offer exactly what the scripted zones make
castable, every time. Today it sometimes offers nothing (evidence table above).

1. **Make it fail locally first.** Loop a scenario start against the real jar and assert the first
   priority window's actionable set (`scenario-start.jvm.test.ts`, new). Start it with `lone-spell`
   (expects Memnite for seat 1) and `bolt-player` (expects Lightning Bolt for seat 0). It loops in-process
   with no browser. Measured CI failure rate on a loaded host is roughly 2–3 starts in 30. Raise the
   pressure until the loop fails: pin the run to one core with `taskset -c 0`, which child JVMs inherit,
   and/or run N matches concurrently in one process. Record the conditions and the failing count in
   `docs/planning/wave37-evidence/A-repro.md`. **If after 45 minutes no condition makes it fail, stop and
   report.** Don't fix a race you cannot see.
2. **Find the cause from Forge's own source** (read-only, `/home/hadoku/repos/hadoku-cardtable/forge/` at
   the pin). Start with `PlayerControllerHuman` (`cachedActionableCards`, `pushActionableCards`,
   `chooseSpellAbilityToPlay`) and `InputPassPriority.showNormalPrompt`, plus the bridge's `seat-N-ui`
   executor. Write the cause, with file:line, in `A-repro.md`. Prove or retract the thread lead above.
3. **Fix it deterministically in the bridge**, and only on the scenario path. The fix must not depend
   on timing. "Null the cache and hope" is today's fix, and it loses. Acceptable shapes: recompute the
   actionable set at the first real priority input after the hook, on the thread that owns it, or
   re-push when the first priority window's set disagrees with a fresh `AvailableActions.collectActionable`.
   No Forge file is changed.
4. **Mutation proof:** under the §A.1 condition, the fix reverted FAILS the loop (with a count) and the
   fix restored PASSES 50/50 for each of the two scenarios. Then run every server-side scenario jvm suite
   from the Blast radius row, **one file at a time**
   (`--pool=forks --poolOptions.forks.singleFork=true`), plus `jvm.test.ts` and `mulligan.jvm.test.ts`
   for the no-scenario path.
5. Bump `apps/server/package.json` patch. Commit; don't push.
6. **Done when:** `A-repro.md` holds the failing condition, the cause with file:line, and the revert-FAILS /
   restore-PASSES counts; every suite in step 4 is green; and, after the manager lands it, `forge-e2e` on
   main passes (see "Wave done-when").

## §E — e2e preconditions

1. **A scenario that didn't apply fails by name, fast.** In `e2e/play/scenario.ts`, after
   `keepBothHands`, have `startScenarioMatch` wait (≤ 20 s, inside the existing budget, with no timeout
   raised elsewhere) until the scripted state is on the board. That means the scripted hand cards are
   in the seat's hand, by name, read from the `.state` file's `humanhand=`/`aihand=`. If they never
   arrive, throw `scenario "<name>" did not apply: <seat> hand is [...]`. **Do not** assert "something
   is offered" here: an empty offered set is exactly the bug §A fixes, and the precondition must be able
   to tell "scenario not applied" from "applied, nothing offered". Run the four scenario spec files
   once each to confirm no caller changes behaviour.
2. **The table-fit red is a second, separate flake.** `table-fit.spec.ts:728` failed on `fba269b`'s run
   with `alice: the ghost and the indicator were drawn`, at host load 12.8. It uses no scenario. Read the
   artifact (`test-results/table-fit-*/error-context.md` and that stack's `play-server-stack-*.jsonl`)
   and write the cause in `docs/planning/wave37-evidence/E-table-fit.md`. Fix it only if the cause is in
   the spec (a fixed wait, a race in the probe). If the cause is in `apps/ui/**`, stop at the write-up:
   that is w38.
3. Commit; don't push.
4. **Done when:** a hand-broken scenario (e.g. a temporary `humanhand=` of a card that doesn't exist, run
   once and reverted) fails with the named error in under 30 s; the four scenario spec files pass once
   each with the jar env (grep the output for `— SKIPPED:`; zero); `E-table-fit.md` exists with a cause
   or with exactly what the evidence did not show.
