## §A — the standard child-app header

The operator asked for the fleet's own child-app header rather than ours. This
is PR-7's first half.

1. Find what hadoku_site's standard child-app header actually is — the
   template at `~/srv/hadoku_site/templates/game/apps/ui/src/` is the
   reference, `@wolffm/task-ui-components`' `AppHeader` is what it mounts.
   **Read it before designing anything**; the answer may be "we already mount
   the same component and the difference is layout", in which case say so and
   fix the layout.
2. Adopt it. Our `AppChrome` keeps only what is genuinely ours: the theme root
   (which the header needs above it), the matchMedia shim (until
   `@wolffm/themes` guards line 216 — see
   `docs/requests/RETRO_UPSTREAM_2026-09-26.md`), and the content container.
3. **Keep the catalogue name.** `__HADOKU_APP_NAME__` resolves "Card Table"
   from `@wolffm/catalogue`; the header must still title from it, and
   `ci:header-fleet` must stay green — it is the fleet's audit and it passes
   today.
4. `RoomChrome` keeps receiving our resolved theme (w20 §E). Do not drop it
   because the header changed; the two are unrelated and the bug is upstream.

5. **Use the fleet's header CSS, do not hand-roll a third set of paddings.**
   The operator, 2026-09-26: *"the top header bar has no left, top, or right
   edge buffer. i would prefer if we reused the existing css that hadoku_site
   ships with child apps for the header bar specifically."* Find what the
   fleet actually ships — `~/srv/hadoku_site/templates/game/apps/ui/src/styles/`
   and whatever `@wolffm/task-ui-components` brings with `AppHeader` are the
   two candidates; **read both before writing any CSS.** If the fleet ships a
   stylesheet we simply are not importing, importing it IS the fix. A wrapper
   to make it sit correctly is ours; the spacing values are not.
6. **The title goes home.** *"'Card Table' at the top should be clickable and
   bring you back to the entry page."* It is a link to `#/`, and it stays a
   real link — keyboard-reachable, not an onClick on a heading. `AppHeader`
   takes a node title for exactly this (the fleet audit reads the node form
   and `header-name` already accounts for it), so this must not break
   `ci:header-fleet`.

Done when: the header is the fleet's, its edge buffers come from the fleet's
stylesheet rather than ours and are correct at 1280×800 and phone width,
"Card Table" still comes from the catalogue AND navigates to the entry page,
and the fleet header audit is green
(`node ~/repos/hadoku-fleet-manager/scripts/check-header-fleet.mjs`).

## §B — the tests that lie

Two suites have passed while proving less than they claim.

1. **`board-play.jvm.test.ts` times out at 120 s** — *"a land and Raging
   Goblin by clicking: not done in 120 s"*, found by the tracker running the
   jar-gated suites (CI never does). Lane B of w20 recorded it passing during
   the wave, so it either regressed after or belongs to the same class as the
   play.spec finding: a real match that never reaches the state the test waits
   for. **Diagnose before changing anything** — a `CARDTABLE_PLAY_DUMP` says
   what the game actually did. If it is the shuffle, seed it (`MatchSpec.seed`
   reaches the JVM through `bridgeConfig`) and make the assertion state what
   it proved. If it is a product regression, that outranks the whole wave:
   stop and report.
2. **Audit the other jar-gated suites for the same shape.** `auto.jvm.test.ts`
   and `jvm.test.ts` drive real games; any assertion whose precondition the
   shuffle grants is the same defect. Seed them, or split them the way
   `play.spec.ts` now is: a scenario that occurred and misbehaved fails; a
   scenario that never occurred reports and does not.
3. **These suites never run in CI** and that is the reason both defects aged.
   Do NOT add them to CI in this lane (the runner has one jar and they are
   slow) — instead leave the board a measured statement of what running them
   costs, so the tracker can decide.

Done when: `board-play.jvm.test.ts` passes for a stated reason, twice in a
row; every jar-gated assertion either cannot fail on luck or says so out loud;
the cost measurement is written down.

## §C — the leftovers the board has been carrying

All three are named on the board and none have moved for two waves.

1. **`fullControl` is not in the match snapshot**, so a refresh draws the
   toggle off while the seat is still in full control (declared in
   `match.ts`). Put it in the snapshot; a reconnect must restore what the
   player chose.
2. **Arrow geometry has never been seen by a human or a browser.** jsdom
   zeroes element boxes, so w20's targeter arrow is asserted on snap targets
   and never on coordinates. Prove it where boxes are real — a Playwright case
   that reads the rendered arrow's endpoints against the two cards' boxes.
   This is the one w20 leftover the operator cannot check for us by playing,
   because a wrong arrow still looks like an arrow.
3. **Combat is not driven by drag anywhere.** `prompts.jvm` exercises combat
   by click; the drag affordance the operator asked for is unproven in
   combat. Drive an attack and a block through it.

Done when: a refresh preserves full control (test); the arrow's endpoints are
asserted in a real browser; combat is driven by drag in a test that asserts
what went on the wire.

## §D — the 0.39.4 cleanups

`@wolffm/rooms-server@0.39.4` is installed and does these properly; we still
carry the workarounds. hadoku_site's adoption note
(`docs/requests/CARDTABLE_GAME_TEMPLATE_ADOPTION.md`) lists them with the
reasons they are safe to delete — read it first, it is the spec for this lane.

1. The re-seat guard after `leaveRoom` (`draftRooms.ts`).
2. `room.seats = state.table` aliasing — use the seat-table factory.
3. `identity.ts`'s hand-rolled `createHash` digest — use
   `createParticipantIdDeriver(domain)`, which **adopted our own domain
   scheme**, so ids do not change. Note it returns `{ id, tier }`, not a bare
   id.
4. `participantHandle` — now `@wolffm/rooms-protocol`'s.
5. **Pad seat views with `seatRows(table)`**, not `Array.from({length})` —
   that drops an occupied seat when `seats.length > capacity`.
6. **Do not delete the disconnect grace.** Watchparty deliberately did not
   take it and they were right; it covers the other ordering. Their note says
   so explicitly.
7. **`packages/room-ask` has no consumer** (O9 on the board). Either give it
   one in this lane or state plainly that it should be deleted — a package
   with no consumer and no owner is a liability. Do not silently leave it.

**A test that goes quiet here is a regression, not a win**: the adoption note
warns the re-seat guard's behaviour is invisible under shipped defaults and is
only observable with `seatHoldMs: 0` AND `disconnectGraceMs: 0`. Re-aim those
tests at the package's behaviour rather than deleting them.

Done when: the four workarounds are gone, ids are byte-identical across the
change (assert it), seat views are `seatRows`-padded, the grace survives, and
`room-ask` has an owner or a stated death sentence.
