# Wave 15 — a real Forge client in a browser, or a measured reason it cannot be

Protocol: `docs/handoff/w15.md` carries it. One manager, one sub-agent per lane,
all parallel, no shared files.

**This wave backs ONE route: CheerpJ.** That is a decision, not a hedge, and
§0 says why. The TeaVM route is parked with its state written down.

## §0 — Why CheerpJ, and what "done" means

Wave 14 asked whether Forge's own client can run in a browser. Two routes came
back alive, and since then the decisive unknown on each has moved:

| route | state after Wave 14 | state now |
| --- | --- | --- |
| **CheerpJ** | GO-WITH-COST, entirely gated on one unexercised probe | **probe passed 2026-09-20.** A Java native blocks on a JS Promise — 153 ms across a deliberate 150 ms await — and round-trips arbitrary bytes through a real WebSocket |
| TeaVM / `forge-gui-mobile` | NO-GO, 53 missing APIs | 53 → **33** after two measured cuts. **libGDX under gdx-teavm remains entirely unattempted** — the largest unknown in the project |

CheerpJ's blocker is solved and its remaining work is three fork changes
**named to the line**. TeaVM's largest unknown has not been touched. Backing
both would halve the attention on each; the operator wants this finished in
two or three waves.

**Done, for this wave, is a number.** The operator set the gate:

> *"if the CheerpJ path is more performant than the streamed path then we
> should go that route instead."*

Streaming has a measured 65 ms click-to-pixel, 1.26 GiB and 0.5 core per
player. CheerpJ has **no number for Forge** — lane B's 123 fps was one
`JComponent`, which it called *"an upper bound on Forge, never a prediction of
it"*. Nothing past `SplashFrame` has ever rendered.

So this wave succeeds if it produces **Forge's real match UI painting in a
browser, with a click-to-pixel figure taken the same way streaming's was**. It
also succeeds if it produces a measured reason that cannot happen. It fails if
it produces an opinion.

## Settled — do not re-open in any lane

- **No money, ever.** This is also why CheerpJ's non-commercial licence fits.
- **The friend gate stays.** `/cardtable/*` is friend-tier at the edge.
- **Never build in the vendored `forge/` tree** (D2). Fork changes are
  **patches** under a lane's own directory, applied to a COPY in `~/.cache`.
  `git submodule status forge` must be unchanged at the end of every lane.
- **Never initialise the `forge` submodule in a worktree**; never
  `git submodule deinit` anywhere.
- **Do not delete the React board.** It is the only thing that plays today. It
  goes when something replaces it.
- **The outer shell is NOT this wave.** hadoku_site's `templates/game`
  adoption is the wave AFTER this one, by the operator's decision of
  2026-09-20. Do not start it, and do not delete `apps/ui/src/chrome/**`.
- **A native fills the array it was handed** (measured 2026-09-20). Inbound is
  `recvLength()` + `recvInto(buf)`, never `byte[] recv()`.

## §A — The transport

The natives probe proved the mechanism. This builds the thing.

1. One class implementing `IToServer`'s three methods over a browser
   `WebSocket`, bound through `cheerpjInit({natives: {...}})`, speaking our
   JSON protocol rather than Forge's Java-serialised one.
2. **The shape is not negotiable and is already measured:** outbound
   `send(byte[])` is fine; inbound must be `recvLength()` + `recvInto(byte[])`,
   because a native that returns a freshly built array throws
   `ArrayIndexOutOfBoundsException` on the Java side
   (`docs/spikes/cheerpj.md`, the SETTLED section).
3. `FGameClient` currently owns a netty transport. Replace its transport, do
   not fork the protocol: our bridge **is** the transport, and the wire it
   speaks is `@hadoku/forge-wire`'s.
4. Deliver as a **patch** under `transport/`, applied to a copy. Do not touch
   `forge/`.
5. Done when: a Forge client inside CheerpJ completes a round trip to a server
   over a browser WebSocket — a real protocol message out, a real one back,
   both named in the log — and the patch reapplies cleanly from a fresh copy.

## §B — Assets and the filesystem

Wave 14 lane B got the stock jar to `SplashFrame` and found two things kill it,
both named to the line:

1. **`getAssetsDir()`** returns `""` for a non-`git` version string
   (`GuiDesktop.java:89-92`); a browser build needs `/app/`. One line.
2. **`res/` without directory walks.** Package `cardsfolder.zip`, relax the
   `isDirectory()` guard at `CardStorageReader:93`, and stop `FSkin` listing
   `CACHE_SKINS_DIR`.
3. **`new ZipFile("/app/cardsfolder.zip")` under CheerpJ was never reached** —
   blocked by that guard. It is listed in lane B's "NOT verified". **Settle it
   first**: if `ZipFile` does not work under CheerpJ, everything after it is
   wasted and the lane should say so on day one rather than at the end.
4. Deliver as patches under `assets/`. Do not touch `forge/`.
5. Done when: Forge boots past `SplashFrame` far enough to have loaded card
   data, with the `ZipFile` question answered either way and the answer stated
   before the rest of the work.

## §C — The server end of the bridge

Independent of CheerpJ entirely, and useful even if CheerpJ fails: the browser
needs something to connect to.

1. An endpoint a browser client joins, terminating its WebSocket and relaying
   to the match's JVM through the existing host (`apps/server/src/play/`).
2. **Reuse, do not rebuild.** `@hadoku/forge-wire` is the wire; the match
   registry, seating and per-seat projection already exist and are proven by
   `jvm.test.ts` against a real Forge. This lane adds a client type, not a
   second play stack.
3. **The hidden-information rule is absolute.** Whatever this serves is
   projected per seat exactly as the existing path is — `jvm.test.ts` measured
   144 secrets in Forge's raw stream and **0** in what reached the seat, and
   that property is not negotiable for a new client type.
4. The friend gate applies unchanged.
5. Done when: a test drives a browser-shaped client through join → a projected
   frame → an act, with a per-seat isolation assertion in the shape
   `jvm.test.ts` already uses, and an illegal cross-seat read fails it.

## §D — First paint, and the number

**This lane owns the decision.** Everything else is plumbing toward it.

1. Build the measurement rig immediately, against whatever renders — even
   `SplashFrame` — so the rig is not on the critical path when A and B land.
2. Take **click-to-pixel the same way lane C of Wave 14 took streaming's 65 ms**
   (`docs/spikes/streaming.md` has the method). A number taken a different way
   is not a comparison, and the operator asked for a comparison.
3. Report cold-load cost too: CheerpJ's runtime is 12–21 MB from a third-party
   CDN per cold cache, which streaming does not pay and which the licence does
   not let us self-host.
4. **State what is being compared.** Streaming's cost is *server* RAM and CPU —
   1.26 GiB and half a core per player on a 12-core host that already runs a
   JVM per match. CheerpJ's is the player's browser. Those are different
   budgets and the recommendation must say which one is binding.
5. Done when: `docs/spikes/cheerpj-firstpaint.md` gives a click-to-pixel figure
   with the method, a cold-load figure, and a recommendation of CheerpJ or
   streaming with the number that decides it. **"Unusably slow" is a complete
   and useful answer** — streaming is costed and waiting.

## The gate, for every lane

`pnpm check` is typecheck + lint + vitest. **It is not the gate.** CI also runs
the browser e2e. Lane C touches `apps/server/**`, so lane C runs `pnpm e2e`
before you land it:

```sh
export CARDTABLE_FORGE_JAR=~/.local/share/cardtable/forge.jar
export CARDTABLE_FORGE_RES=/home/hadoku/repos/hadoku-cardtable/forge/forge-gui/res
pnpm e2e
```

`export` them: `VAR=x cmd1 && cmd2` sets them for `cmd1` only, which made a
Wave 12 run **skip** its test and exit 0.
