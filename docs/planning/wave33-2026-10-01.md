# Wave 33 — a game a test can set up, so a human never has to wait for it

Protocol: `docs/handoff/w33.md` carries it. **Five lanes, all dispatched at t=0.**
Implementers commit and stop; the manager verifies from artifacts and lands lane by
lane, **in ONE push at the end**.

**Why this wave exists.** Wave 32's closing notes admitted that **Q7 and Q10 passed their
e2e vacuously** (the monitor reached turn 5 and met zero stack asks and zero Declare
Blockers windows), that Q14 and Q8 were never driven against real Forge, and that no test
asserts the active-player ring. The tracker's re-run then found two more e2e tests that
fail **3 of 5** runs (the combat rail, the concede test) and **neither runs in CI**
(`forge-e2e` runs only `play.spec` and `table-fit.spec`). The operator does not want
another play-test spent finding things a test should have found. So the first job is a
game a test can SET UP: a scripted starting state, then a spec per feature that cannot
pass unless the feature happened. The bugs that were waiting on it ride along.

## Settled — do not re-open in any lane

- **Your own spell no longer holds priority (Q17).** w32 changed the default. Operator,
  2026-10-01: *"i'm fine with those changes."* Do not revert it.
- **The single layout is always two tiers, so a board of six or fewer permanents has
  smaller cards than before.** Same ruling; do not revert it.
- **A scenario is a TEST facility, never a production one.** It is honoured only when the
  server runs with `CARDTABLE_PLAY_PROBE=1` (`apps/server/src/index.ts:388`). Production
  does not set it. A request carrying `scenario` without the flag is refused, not ignored.
- **A spec that cannot fail is not a spec.** Every new e2e asserts, before it asserts the
  behaviour, that the situation it tests occurred (a stack ask was opened, a blockers
  window was reached), and fails if it did not. No test in this wave may pass because the
  game never got there.
- **Nothing is called verified that no test exercised.** A closing note says "unit-tested
  only" when that is the case. (w31 and w32 each shipped a lane that said "verified" for a
  path no test reached.)
- **No Forge change and no jar install this wave.** `forge/` stays pinned at `917bb193`.
  If a lane finds one is needed it stops and reports.
- **The earlier rulings stand:** no WotC trademarks, no money, friend gate, no image bytes
  in the bundle; chrome colours follow the theme, colour-pie hues and shadows stay fixed.

## §S — Scenario harness and server scenarios

The bridge is one Java source file we own, run by the source launcher
(`PlayBridge.java`, no build step), and Forge's own `GameState` is what its puzzle mode
uses to set up a position. `GameState.applyToGame(game)` is public
(`GameState.java:582`), and `HostedMatch.setStartGameHook(Runnable)` runs a hook inside
`startFirstTurn` (`Match.startGame` → `GameAction.startGame:2373`), after the mulligans, which
is where puzzles apply their state. The bridge returns `null` from `getGamestate()` today.

1. **The harness (shape 1).** `scenario` goes from the route (`socket.ts`'s create body,
   guarded by the same unknown-field check as `names` and `avatarIds`) to the bridge, which
   parses it into a `GameState` and applies it from the start hook. **Verify on a real
   match first** (whether `applyToGame` is safe to call on the game thread from the hook, or
   needs the `invoke` it already does); evidence in `wave33-evidence/s1-harness.md`. Seats keep
   their normal identity; the mulligan still happens and a test answers it with a keep.
2. **Scenarios as files.** `apps/server/src/play/scenarios/*.state` plus a README of the keys
   a test needs. Write the ones the specs need, each small and named for the claim it
   proves: `lone-spell` (the opponent casts a spell and you hold a counterspell, Q7),
   `no-creatures` and `one-creature` (Declare Blockers, Q10 and Q12), `two-triggers`
   (Q8), `own-spell` (Q17), `glint-hawk` (a permanent with an activated ability whose own
   trigger is on the stack, Q18), `attackers-declared` (Q14), `ponder` (Ponder on the
   stack, for its text), `auto-target` (an effect with exactly one legal target on the
   stack, for the Fiend Hunter arrow).
3. **A real-Forge test per scenario** (`*.jvm.test.ts`, one file at a time), asserting what
   the SEAT is offered, not that the code ran: Q8 no ordering ask without full control and
   one with it; Q10 no blockers stop with no creatures and one with a creature; Q17 the
   caster does not hold priority after casting and does in full control; Q12 the block
   prompt arrives and blockers can be assigned; and **the wire carries `TargetCards` for the
   `auto-target` scenario**, which decides whether the Fiend Hunter arrow is a UI task (it is
   expected to be; say so if it is not).
4. **The concede race (the manager called it "failed once"; it fails 3 of 5).**
   `e2e/w31.spec.ts` "concede ends the game" waits for a `concede-refused` log line. The
   server's guard sits ahead of the status check (`match.ts`, `fromClient`), so find out why
   the line is sometimes absent: a second concede that arrives while the status is still
   `running`, or the c2s frame never reaching `fromClient`. Fix the cause if it is the
   server's; if it is the test's observation, say so and E fixes the test. Evidence in
   `wave33-evidence/s4-concede.md`, with the failure rate **before and after over ten runs.**

**Done when:** `pnpm check` exits 0; the harness works against a real match with the flag and
is refused without it (a test for each); every scenario has a real-Forge test that fails when
its feature is reverted (counts, naming the suite); the concede evidence file exists.
