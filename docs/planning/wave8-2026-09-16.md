## §A — Replace Tier C's refusal with a schema

`setGameView` · `openView` · `applyDelta` — the three methods that carry the
whole game state.

1. Model them from **the spike's captured data**, not from reading Forge and
   guessing: `scripts/spike/tierc/` produced real packets from 12 real games.
   A schema derived from live captures is checkable; one derived from a class
   definition is a hypothesis.
2. Wave 7 found **no object references cross the wire** — `TrackableObject`
   references are already swapped for `IdRef` markers — and that **54 of the
   encoders lane F budgeted turn out to need nothing**. Do not write encoders
   for values that are already plain.
3. **Keep the events arm out of this lane.** A `DeltaPacket` carries state *and*
   events; they are different problems and lane B has the second one. Model the
   events field as an opaque arm that defers to lane B.
4. Done when: the refusal is gone, the three methods validate against captured
   packets from the spike, and a mutation to a captured packet fails validation
   with the path named.

## §B — The events arm: 36 schemas, and the trap

The long pole, sized at 1–2 days by the spike that found it.

1. **36 distinct `GameEvent` classes fired across 12 games, of 58 declared.**
   Model the 36. For the other 22, **refuse explicitly** in the same style
   `tier-c.ts` used — a named refusal pointing at what would settle it beats a
   schema nobody has seen data for.
2. The source data is Java-serialized bytes wrapped in
   `TrackableSerializer.WrappedEvent`. **The output must be JSON a browser can
   act on.** If a given event cannot be expressed without reaching back into
   Java, say so and name it; that is a finding, not a failure.
3. Derive from captured events. The spike's capture harness can be re-run:
   `bash scripts/spike/tierc/run.sh capture -Dtierc.games=12`.
4. Done when: 36 events have schemas validated against captured instances, the
   remaining 22 refuse by name, and the closing note says how many of the 36
   were expressible without Java-side help.

## §C — The board renderer

The "month" from lane F's estimate, started. **This lane renders; it does not
connect.** No socket, no server, no protocol.

1. Render a board from a **fixture** of Tier C state — the same discipline that
   made the draft UI work, and which let the draft's transport be swapped later
   without touching a component.
2. Zones: battlefield, hands (counts for opponents), graveyards, exile, stack,
   life totals, turn and phase. Card tiles already exist (`components/CardTile`)
   and already render our own art and pips — **reuse them, do not fork them**.
3. **D13/D15 still bind.** Art comes from the art resolver; our origin never
   serves an image; no WotC marks in chrome we draw.
4. **Commit the fixtures.** They are the contract with lane A's schema and the
   regression net for everything after.
5. Done when: a board renders from a committed fixture at a real game state,
   the fixture validates against lane A's Tier C schema (the manager runs this
   after both land), and the layout survives a phone-width viewport.
