## §A — Make it boot every time

**The blocker.** `res/` unpack fails roughly one boot in two. Everything else in
the CheerpJ route is measured and working; this is why the wave's number does
not exist.

1. Find the actual failure, not a retry. A retry loop around a race turns a
   visible bug into an intermittent one, and this project has enough of those.
2. The unpack path is lane B's and this lane's patches from Wave 15 —
   `cardsfolder.zip`, the `isDirectory()` guard at `CardStorageReader:93`,
   `FSkin`'s `CACHE_SKINS_DIR` listing. Start there.
3. **Report the failure rate before and after, from the same number of runs.**
   "It seems better" is not a result; `n` boots, `k` failures, both times.
4. Done when: 20 consecutive cold boots reach Forge's home screen, the failure
   mechanism is named by file and line, and reverting the fix reproduces the
   failure at its original rate.

## §B — Take the number

**The route is DECIDED. This lane validates, it does not choose.**

Operator, 2026-09-20, on seeing Wave 15's comparison: *"CheerpJ looks like it's
saves us ~150ms latency so that seems like a better experience."* That is a
correct reading. Streaming pays **2 × RTT on every click** — up with the click,
back with the pixels — while CheerpJ pays **nothing** for anything the UI
answers locally, and Magic is mostly looking at a board. On a 50 ms link that is
~100–150 ms per local interaction, and ~1 RTT on the actions that move game
state.

So a slow number here **does not** send us back to streaming. What it changes is
what we ship and what we tell players. Take it anyway, for three reasons:

- The 49.5 ms it is being compared against is a **floor** — one Swing component.
  Real Forge is slower and nobody knows by how much.
- A local interaction budget is the thing that decides whether the *board* needs
  work later, and how much.
- If real Forge lands somewhere genuinely bad — a number where a card game stops
  feeling like one — the operator should hear it early, not after the shell is
  wrapped around it.

The old framing follows, for the method.

1. The rig exists and is validated against both CheerpJ and streamed Forge
   (`firstpaint/rig.js`, `run.sh forge-measure`). This lane runs it against
   **Forge's real match UI**, not a component floor.
2. **event→pixel, the same protocol as `rfb-latency.py`'s**, which lane D of
   Wave 15 already mapped term by term. Not press→pixel — that is the error
   this project just corrected.
3. Report min / median / p95 / max and dropped clicks split by cause, as both
   previous measurements did.
4. **A bad number is a complete answer** — it just is not a veto any more. Say
   it plainly and let the operator price it.
5. Done when: `cheerpj-firstpaint.md` carries an event→pixel figure for **real
   Forge**, beside streamed Forge's ~13.6 ms, with the method stated and the
   run count given.

## §D — Adopt the fleet's shell

Source, and read the CURRENT version rather than any summary — it has been
revised twice mid-flight and both revisions were substantive:
`/home/hadoku/srv/hadoku_site/docs/requests/CARDTABLE_GAME_TEMPLATE_ADOPTION.md`

1. **Upgrade to 0.39.4** (not 0.39.3 — they revised it).
2. **The four deletions**, all verified by the tracker to exist at the lines
   named: the re-seat guard (`draftRooms.ts:378`), `room.seats = state.table`
   (`:230`), the `createHash` digest and `participantHandle`
   (`identity.ts:35`, `:132`). They adopted our
   `hadoku.cardtable.participant.v1` domain, so **ids do not change**.
3. **Two API shapes will not typecheck silently:**
   `createParticipantIdDeriver(domain)` returns `{ id, tier }`, not a bare id;
   and per-tier separation is enforced inside the package, so there is nowhere
   to pass a second domain string.
4. **`seatRows` and deletion #2 are ONE change, not two.** Our seat rows come
   from the engine (`packages/draft/src/view.ts:54`,
   `Array.from({length: state.seatCount})`), and `room.seats = state.table` is
   what keeps seating single-sourced — `draftRooms.ts:14-21` explains that two
   tables would be two answers to "which seat is Alice in". **Taking the
   deletion without routing the engine's table through the factory introduces
   the exact bug `seatRows` exists to prevent.** Do both or neither.
5. **`onRoomDelete` first, GC second — never the reverse.** We deliberately
   never delete rooms (`draftRooms.ts:79-86`: `collectGC` would reap every
   forty-five-minute draft the moment a blip hits the last connected player).
   If this lane enables GC it must adopt the hook first, or it leaks the
   `vacating` timers and a match's JVM handle. **Re-taking the no-GC decision
   is the operator's, not this lane's** — adopt the hook, leave GC off, report.
6. **Do NOT delete our disconnect grace.** Watchparty deliberately did not take
   it and they were right: it covers the other ordering, where a refresh drops
   the old socket ~36 ms *before* the new one joins.
7. **`apps/ui/src/chrome/**` is NOT this lane's** and not in this wave. The
   operator wants our wrapper removed in favour of the template's, but that is
   a UI change against a UI whose future depends on §B's number. Report what

### §D's trap, which hadoku_site warned about explicitly

> *"Whatever currently pins your re-seat guard now passes because the PACKAGE
> does it. That reads as coverage and is not."*

**A test that goes quiet rather than red.** This project has hit that shape six
times and it is the single most expensive pattern in its history.

It is only observable with **both `seatHoldMs: 0` and `disconnectGraceMs: 0`**,
where a seat is empty, unreserved, and the next arrival takes it while its owner
is still connected on another tab. Under shipped defaults the grace and the
reservation each hide it.

**Re-aim that test; do not delete it**, and say in the closing note which test
it was and what it asserts now. `templates/game/apps/server/test/rooms.test.ts`
runs a second server configured that way for exactly this.
