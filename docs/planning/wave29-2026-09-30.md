# Wave 29 — you aim from where the card is, active abilities say so, and your avatar reaches your seat

Protocol: `docs/handoff/w29.md` carries it. **Two lanes, both dispatched at t=0.**
Implementers commit and stop; the manager verifies from artifacts and lands lane
by lane.

**This wave is deliberately small.** Wave 28's manager measured its own clock
(`docs/planning/wave28-evidence/manager-why-waves-run-long.md`) and found the
wave cost ~110 minutes where ~55 would have done, because the biggest lane
carried eleven items and started at minute 55. Test execution was 10–20 minutes
of it; the rest was agents reading and editing. **The play surface can only ever
be one lane, so that lane IS the wave, and the fix is fewer items in it.** Three,
this time.

## Settled — do not re-open in any lane

- **No lane ordering. Both lanes start now.** Where a dependency exists it is
  written as a TASK below, with the contract stated, so neither lane waits on the
  other to begin.
- **The avatar's join key already exists and is not up for redesign.**
  `seats[].playerId` is Forge's player id for a seat and is already in the join

  player id. The hop needs a field to carry, not a new correlation.
  `docs/planning/wave28-evidence/D-avatar-field.md` §2 traced it and §3 fixes the

  Forge renders into its own view, and `socket.ts:250` says so: *"Forge shows
  these names to both seats; they are never an identity."*

  (`match.ts:933`) broadcasts per-recipient, damage is `--c-red` in the log, and
  `live__log-card` makes names hoverable.

## §A — The play surface (items 17, 16, 4-render)

You own `apps/ui/src/play/` whole because it cannot be split: `Board.tsx` is
pinned by ten test files across four of its subdirectories. **Three items, on
purpose.**

**Item 17 — you aim from where the card is.** Operator, 2026-09-28: *"the arrow
drawing is very wonky, by default it points at player portraits which doesnt make
sense at all. when playing a card, it should get put in the 'decision area' and
the arrow should draw from there, at least thats whenever i'm playing a card that
has an arrow that needs drawing."*

1. **An arrow must not default to a player portrait.** With no target under the
   pointer it points at the pointer, or at nothing — not at a seat.
2. **A card being played moves to a staging area, and the arrow starts there.**
   That area sits beside the question panel wave 27 §B gave a fixed home
   (`live.css`, the stack/question column at ~59% across), so design them
   together rather than adding a third floating thing.
3. `e2e/arrow.spec.ts` is yours; it measures the arrow's endpoints against both
   cards' boxes and will need re-aiming.

**Item 16 — an active ability says so.** Operator: *"things like morbid should be
visible when they are active. the 'orange glow' from hearthstone was always nice
for when cards special effects were active."*

**Two things wear this coat and only one is buildable. Ship that one.**

4. *"This card can do something right now"* — build it. The wire carries
   `HasAvailableActions` and `CanPlay` (`packages/forge-wire/src/tier-c.ts:483,486`,
   both `BooleanType`), and Forge's actionable set already arrives as
   `setWeaklySelectable`. A glow driven by those is most of the effect described.
   It must not collide with the SELECTION and ATTACK-INTENT outlines the gesture
   layer draws, nor with wave 28's state layer — a fourth outline colour is not
   the answer.
5. *"Morbid's condition is currently met"* — **check before promising.** Nothing
   obviously on the wire says a named conditional ability's condition is
   satisfied; the nearest candidates are `OverlayText` and `MarkerText`
   (`tier-c.ts:373-374`, real `CardView` getters). **If Forge does not tell us,
   computing it ourselves is implementing rules, which this repo does not do** —
   the answer is then a bridge change and NOT this wave. Report which it is, with
   the evidence.

**Item 4 — the avatar reaches the seat.** Wave 28 got it as far as the table
view; `PlayerFace` still draws its generated bust.

6. Read the per-seat avatar off the MATCH state — not off Forge's `PlayerView` —
   and join it to `BoardPlayer` by `playerId`, which the seat envelope already
   carries.
7. **Build against this contract from minute zero; do not wait for §B.** §B adds
   the avatar beside `playerId` in the join envelope's seat list
   (`socket.ts:648`, `seats.map(s => ({ seat, claimed, playerId }))`). Agree the
   exact field name with the manager in your first report if you need to; the
   shape is a nullable string id.
8. Keep the generated bust as the fallback, and honour §3 of
   `D-avatar-field.md`'s three-state rule so your fallback and the server agree: a
   seat with no avatar is not the same as a seat whose avatar has not arrived.

**One constraint on `adapter.ts`, which is yours.** Two tests pin it from
directories NO lane owns — `apps/ui/src/components/ManaPip.test.ts` and
`packages/carddata/src/art/ids.test.ts`. **Add to its exported shape, never
change it.** If you are certain a signature must change, stop and report.

Done when: `pnpm check` green; a `Board.test.ts` or `gestures.test.ts` case per

## §B — The server carries the seat's identity (item 4, server half)

Four files, one field, and the route is already traced in
`docs/planning/wave28-evidence/D-avatar-field.md` §2 — read it before you start,
because it names what each file must do and why one obvious shortcut is wrong.

1. `routes.ts`: `startFromRoom` already holds both `TablePlayer`s when it rewrites
   `req.body` to `{ opponent: 'human', decks }`. Add the per-seat identity in the
   same seat order the decks are in.
2. `socket.ts`: carry it on the match spec as a per-seat identity field **beside**
   `deck` and `ai`. **Not on `seats[].name`** — see the settled note.
3. `match.ts`: the seat table is where it belongs (`Match` already holds a seat's
   `owner` from `claim`). Put it beside `playerId` in the join envelope at
   `socket.ts:648`, which is the field the client uses to line a seat up with a
   Forge player.
4. **Do not leak it to the other seat's Forge view.** The names Forge renders are
   deliberately anonymous; an identity is for OUR client, not for Forge's.
5. If a `*.jvm.test.ts` under `apps/ui/src/play/live/` moves, report it with the
   failure and **at most one reverted run per suite** to attribute it. Those files
   are §A's.

Done when: `pnpm check` green; a `socket.test.ts` case proves the join envelope
carries the avatar beside `playerId` and that a seat with none carries the
absent state rather than an empty string, and a `tables.test.ts` case proves
`startFromRoom` puts the right identity on the right seat — both failing when
reverted, **with counts naming the suite**; and the note gives §A the exact field
name and shape.
