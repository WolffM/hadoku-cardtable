# Wave 13 — rooms first: a list you join, a type you pick, a deck each, then a game

Protocol: `docs/handoff/w13.md` carries it. One manager, one sub-agent per lane,
all parallel, no shared files. Implementers commit and stop; the manager
verifies from artifacts, lands lane by lane, confirms the deploy.

## The flow, in the operator's words (2026-09-19) — this is the spec

> 1. players go to cardtable and all they see on the front page is a list of
>    rooms and they can either join a room or create a new one.
> 2. once inside a room, the room leader can set what the game type is
>    (constructed 1v1, or draft room …). so constructed 1v1 is the simplest to
>    go for first.
> 3. once the room type is set (which should be doable from the create room
>    screen also), players can load up the decks.
> 4. then once both players have a valid deck loaded the game can be started.

And: **"every friend sees every room, and should be able to enter any room
unless the room is password protected."**

### Why today's screen is wrong, so nobody rebuilds it

`POST /api/play/matches` takes `decks: [a, b]` in ONE call, because Forge needs
both decks when the match starts. That server shape leaked into the product:
the UI made **one person choose both players' decks** and reduced the room to
an invite link. The operator's reaction was exact — *"this is not how any of
this should work"*.

The inversion: the ROOM holds per-player state, and the server assembles the
two decks and calls Forge **once both players are ready**. The per-seat
validator (`POST /api/tables/check`) is already per-deck and does not change.

- **The friend gate stays.** `/cardtable/*` is friend-tier at the edge. A room

- **Draft rooms with sub-pods are OUT of this wave.** The operator said

## §A — Rooms: registry, list, passwords (PR-3 × PR-5)

`@hadoku/room-store` has been built, tested and **unused** since Wave 5 — the
board has carried it as `watch`, "no consumer". This is its consumer.

Watchparty deliberately keeps `cardtable-*` rooms **out of their lobby**
("never listed", their 0.39.0 note), so the room list is ours. Their chrome
gives chat and roster INSIDE a room; our server says which rooms exist. That
split is correct and is not a gap to close.

1. A room has: an id (matching `[a-z0-9-]{1,40}` so `roomKeyFor` accepts it —
   see `apps/ui/src/room/RoomShell.tsx`), a name, a creator, a **game type**
   (`constructed-1v1` for now; leave the type open for `draft` without building
   it), members, and an optional password.
2. `GET /api/rooms` lists every room to any friend-tier caller — the operator's
   rule is "every friend sees every room". A listing **never** includes the
   password or its hash, and says only *whether* a room has one.
3. `POST /api/rooms` creates; `POST /api/rooms/:id/join` joins. The **game type
   is settable at creation** and by the room leader afterwards.
4. **The password is privacy between friends, not authentication.** Everything
   here is already behind the friend gate, so this keeps a sibling out of your
   game; it is not a security boundary and the lane must not build it as one or
   describe it as one.
   - **Never store it in plaintext** and **never log it** — not at debug level,
     not in an error, not in a room dump.
   - Rate-limit attempts per caller. `@wolffm/rooms-server` already ships rate
     limiting; use it rather than inventing one.
   - A wrong password and a missing room return the **same** response. A
     different 404-vs-403 tells an enumerator which rooms exist.
5. Persist through `@hadoku/room-store`. A room and its membership survive a
   restart; **the deploy that follows this wave is the test.**
6. Done when: `GET /api/rooms` lists rooms created in a previous process, the
   password never appears in any response body or log line (a test greps the
   captured log, not just the body), a wrong password is indistinguishable from
   a missing room, and the closing note gives the room JSON shape verbatim so C
   can code against it.

## §B — The front page is a room list (PR-2 × PR-3)

`LobbyScreen` today is "start a pod, or join one". It becomes the room list the
operator described: the first thing you see, every room on it, join or create.

1. List every room from `GET /api/rooms`: name, game type, who is in it,
   whether it is locked. Empty is a real state and gets a real empty view, not
   a spinner that never resolves.
2. Create a room, **setting the game type on the create screen** — the operator
   asked for that explicitly.
3. A locked room prompts for the password **at join**. A wrong one says so
   without saying whether the room exists.
4. Entering a room navigates to it; the room's own screen is C's.
5. **Do not mount a `RoomChrome`.** `App` already does, once. A second one
   shares and then tears down the first's socket.
6. Done when: the front page lists rooms from the server and creates one with a
   chosen game type; a locked room cannot be entered without its password; and
   the empty, loading and failed states each render something a person can act
   on, proven by a test per state.

## §C — In-room constructed 1v1 (PR-4 × PR-5)

This is the lane that undoes the screen the operator rejected.

1. Inside a room, **each player loads their OWN deck**. Nobody picks anyone
   else's. Each deck is validated on its own through the existing
   `POST /api/tables/check`, which is already per-seat and needs no change.
2. Each player readies up. The UI shows both players' state — chosen, valid,
   ready — because "waiting for the other person" is the screen's main job.
3. **The server starts the match** when both are ready, assembling the two
   decks from room state. A client must not be able to start a match by
   sending two decks of its own choosing: that is the shape being removed, and
   a test must prove the old path is closed.
4. The deck the gate validated must be the deck Forge plays — Wave 11 lane D
   made those the same bytes and Wave 12 lane B kept them so. Do not
   reintroduce a second reader.
5. Until A lands, code against §A's room JSON as a written type and say so.
6. Done when: two participants in one room each load their own deck, ready up,
   and a match starts without either choosing the other's deck; a client
   POSTing two decks directly is refused, with a test; and an invalid deck
   blocks only that player's ready, naming the offending card.

## §D — A drafted deck with basic lands cannot be played (PR-2 × PR-4)

Found by Wave 12 lane B, confirmed by the tracker by execution: add 17 Islands
to a drafted deck and the server refuses it — *"plays 17x Island but drafted
0"*. **The whole draft half of the product is unplayable until this is fixed**,
because a 45-card pool is not a deck until you add lands.

Mechanism, verified rather than assumed:

- `deckFromDeckFile` returns `basics: []` and leaves the lands in `main`
  (`packages/deck/src/deck.ts:311`), because a `.dck` has no basics section.
- `poolOf` is `main + sideboard` (`deck.ts:138`).
- The draft arm compares that whole thing against the drafted pool
  (`apps/server/src/http/gate.ts:346`).
- `deckIssues` has **no** basic-land exemption on the pool arm — it only checks
  `deck.basics` for "is in the basics pile but is not a basic land", and that
  pile is always empty on this path.

1. Split basic lands out before the pool comparison. `isBasicLand` and
   `BASIC_LAND_NAMES` already exist (`deck.ts:119`, `:40`) — Forge's own five
   names from `MagicColor.java:138`. Do not invent a second list.
2. **Basics are exempt from the POOL check only.** Every other rule still
   applies: a non-basic the caller did not draft is still refused, and a card
   named in the basics pile that is not a basic land is still refused.
3. Do not weaken the constructed arm. A Standard deck's lands are checked
   against the format pool and must stay checked.
4. Put the new tests in `gate.test.ts` (new). `tables.test.ts` is C's.
5. Done when: a drafted deck with 17 Islands is accepted and starts a match; a
   drafted deck with an undrafted non-basic is still refused by name; reverting
   the fix fails a named test; and the closing note quotes both verdicts.
