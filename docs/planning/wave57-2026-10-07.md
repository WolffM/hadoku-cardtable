## Settled — do not re-open

- **The server decides before the seat sees.** A window the server will answer is never drawn, pace delay
  or not. Hold a `showPromptMessage` until its `updateButtons`; decide once on the pair; forward both or
  neither. A window no decider can read (InputAttack's per-click refreshes, a status line) is never held —
  that is the narrowing w55 found, and the 2 s lag is the test for it.
- **A second prompt never drops the first** (the overwrite-drop bug): a pending pair is flushed as
  forwarded when a newer prompt arrives for the same seat before its buttons do.
- **Every one of the eight suites is proven on a jar before landing**, plus the six unaudited jvm readers
  and the four unaudited e2e specs. A red there is this contract's and is fixed here, never pinned.
- **The bar stays coherent for the seat:** when a window is withheld, the seat's buttons go out disabled
  (as `maybeConfirmChosenCost` does today), so the control box never shows a live OK for a question that
  was never shown.
- Telemetry: the `prompt-forwarded` / `prompt-withheld` events and the frames ring as built; measure the
  ring on one real 20-turn match and put the numbers in the note; no new store, no endpoint.

### Why the w55-S tree was red, and what changed (none of S's guesses held)

S read 6–7 of the 8 as the overwrite-drop bug. The first claw run had both of S's fixes in and all 8
stayed red. From the dumps, the timelines and Forge's own inputs:

1. **A stale bar decided the next window** (phyrexian, cast-hidden). `InputPayMana` sends a lone `Auto` bar
   after a payment completes (`InputPayMana.java:349`). S's hold parked it and paired it with the caster's
   next `Priority:` prompt, decided on that mismatched pair (kept: `Auto` is not live), and the real OK
   bar went out live and undecided. Nobody passed, so the spell sat on the stack. The fix (435de13) pairs by
   each input's order. A `Priority:` prompt takes the bar after it (`InputPassPriority.showNormalPrompt`); a
   payment or confirm prompt takes the bar before it (`InputPayMana.updateMessage`,
   `InputConfirm.showMessage`). A newer bar replaces a held one, and a newer prompt pushes a held one out
   forwarded. This also stops an auto-paid payment's disabled `Auto` bar (live Cancel) from reaching the
   seat. S's tree forwarded it via the overwrite flush, so Bitterblossom still flashed a bar.
2. **A re-shown confirm reached the seat** (Augur). Forge sent "Sacrifice Augur of Skulls?" and its Yes/No twice,
   1 ms apart. The first copy was auto-confirmed and withheld, the second was "kept" and drawn. 9eda252: the
   window last answered for a seat is remembered until Forge sends that seat any other frame, and an
   identical pair in that time is withheld without a second press.
3. **Suites reading the seat's wire for a window that is now withheld** (Q17, priority, cast-hidden manual
   pay, Q8 ×2, Q12's post-block step). They asserted, as a precondition, that the window was drawn. They now
   read Forge's own frames (`scenario.ts` `forgeFrames`), and Q17 and priority also assert the window never
   reached the seat.
4. **The harness answered windows for the seat** (Q12, Augur). `finishMulligan` called `keepHands()` (OK on
   any enabled non-`Priority:` prompt) until both seats' *wire* prompts left the keep question. With the
   first priority window withheld, the defender's wire stayed on "keep your hand?" until the block input
   arrived, and `keepHands` declined the block. Q12's `known_flaky` pin says "the block input opens and closes
   with nobody pressing, 3 of 4 runs", which is this. Now `finishMulligan` presses only the opening questions
   and reads Forge's prompts.
5. **prompts-offboard:174 never declined anything, on main either.** Its driver returned on the pre-cast
   "Stack: Empty" says line (`expect.poll` runs at once), and the "no lock" live OK it then found was the
   cast's own *flashed* payment or priority window, which is AB11 itself. The board answers a
   one-ability `getAbilityToPlay` by itself (`apps/ui/src/play/prompts/rules.ts` `autoAnswer`), so the
   trigger's "you may pay X" offer is only drawn under Full control. The test now turns Full control on,
   declines by None, and waits for the stack to empty and both offers to close (12/12).
6. **combat-drag.jvm** (second full run). InputAttack's last refresh ("Select creatures to attack null…",
   bar dead) stays the seat's latest prompt through the combat steps the server now passes. The driver read
   the text alone and dragged a land at the face; the board correctly sent nothing, and the suite counted
   it as a gesture. The driver now declares only while the input's bar is live.

The w55-S narrowing is proven: Q14 (`w33:248`) is green in every e2e run, from the first.

### Decisions

- Pairing follows Forge's per-input order rather than arrival. A payment or confirm prompt that arrives
  *before* its bar is not a Forge order (`InputConfirm`, `InputPayMana` always send the bar first). The
  wave-52 unit test that pushed it is deleted; its sibling with Forge's order stays.
- Superseded bars are dropped, not forwarded: a bar is state, and only the latest is drawn.
- `finishMulligan` (scenario.ts) changed shape for every jvm suite that uses it; the full run is green on it.
- Out of Owns, minimal, reported: `apps/ui/src/play/live/combat-drag.jvm.test.ts` (one condition in its
  driver). Not touched: `.github/workflows/forge.yml`. **Q12's `known_flaky` pin can go**: its documented cause
  was item 4, and Q12 is green in both full runs since.
