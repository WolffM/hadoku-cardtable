## What the tracker verified (origin/main 28c2d2a3d)

- **The error is the replay player's own design.** `apps/ui/src/replay/replayTransport.ts` is a
  `MatchTransport` that pretends to be a socket so it never has to touch `match.ts`. Its header says:
  *"feeding its registered `forge:s2c` handler one frame whose cursor is an obvious gap is exactly
  what a resync is for"*. To seek, it sends a frame at `seq + 1_000_000` (`:217`), and `match.ts`
  resyncs against `request`'s snapshot.
  `match.ts:2797` `MAX_RESYNCS_WITHOUT_PROGRESS = 3` is the live socket's guard against a server
  whose snapshots never catch up. Any replay sequence that answers a resync without progress trips
  it, and the message blames "the server's snapshot cursor". Which sequence the operator hit is
  **not measured**: reproduce it first.
- **Prod's recordings are clean.** Only 3 exist in `~/srv/hadoku-cardtable/apps/server/data/recordings`,
  111, 564 and 161 frames, each with one epoch and zero seq gaps. PPE has none. Explain why there
  are so few (retention is 7 days, `retention.ts`, so count matches against recordings).
- **The e2e never plays a real game.** `e2e/fp-replay.spec.ts` replays a match that ends by concede on
  its first turn and compares zone counts. Nothing covers a multi-turn game, a seek, a speed change,
  the front page's loop, hidden hands, art, or load time.
- The recording is the watcher channel (`docs/planning/front-page-and-replay-plan.md`). It carries no
  hidden hands, so "both hands face up" is a recording change, not a drawing one. The plan's own gaps
  (no arrangement/placement echoes in the stream, no watcher channel for AI-vs-AI) are yours to
  close or to rule out in writing.
- No replay endpoint sends a cache header (`apps/server/src/http/replays.ts`).
