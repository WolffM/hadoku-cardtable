# Wave 2 — a cube draft you can play end to end, with no room and no socket

Protocol: `docs/handoff/w2.md` carries it. One manager, one sub-agent per lane,
all parallel, no shared files. Implementers commit and stop; the manager
verifies from artifacts and lands lane by lane. This repo has **no deploy
target**, so "landed" is "on `main`, pushed, and CI green" — which is now a real
check: the remote exists and CI has run.

The wave is deliberately **transport-free**. Watchparty published P0–P2-core on
2026-09-14 and we now depend on one of those packages, but nothing this wave
opens a socket, mounts the room chrome, or imports `rooms-server`. A pure engine
plus a declared wire shape means wiring in Wave 3 is wiring, not a rewrite.

## §A — Card resolution and draft recipes

Wave 1 shipped a `.dck` parser, 95 cube lists, and a Scryfall ingest that writes
`cards.jsonl`. Nothing yet turns `1 Stoneforge Mystic|PRM` into a real card, and
that resolution is the genuinely risky part: **47,315 card lines across the 95
cubes carry a set code, 72 are a bare name**, and they reference **375 distinct
set codes** — Forge's codes, which are not always Scryfall's.

1. Parse Forge's `.draft` recipe format and import all 94 files from
   `forge/forge-gui/res/draft/*.draft` into `drafts/` (read-only from `forge/`,
   byte-identical, same as Wave 1 did for `cubes/`). Seven keys: `Name`,
   `DeckFile`, `Singleton`, `Booster`, `NumPacks`, `NumPlayers`, `LandSetCode`.
   Parse the one `Booster: 5 Rare, 1 Mythic, 5 Common, 5 Uncommon` too — do not
   special-case it away, it is a legal recipe.
2. A resolver: `(CardRequest, cache) -> GameplayCard | Unresolved`. Prefer an
   exact `name` + `set` + `collector_number` match, then `name` + `set`, then
   `name` alone taking the earliest non-digital printing. **Never guess
   silently** — an unresolved reference is a returned value, not a throw and not
   a `null` that becomes a blank card on a draft table.
3. Run it over **all 95 cubes** and commit the resolution report as data: how
   many resolved at each tier, and the full list of unresolved references with
   the set codes that failed. This number is the lane's deliverable — a cube
   that is 97% resolvable is not draftable, and we need to know which ones those
   are before lane B builds packs out of them.
4. **No image code path, still** (D13). The Wave 1 control must keep biting.
5. Done when: `drafts/` holds 94 recipes that parse; the resolver runs over all
   95 cubes against a live-synced cache; the report is committed; and
   `grep -rniE "\.jpg|\.png|image_uris|scryfall\.io" packages/carddata/src`
   returns **nothing**.

## §B — The pure draft engine, and the wire shape

Transport-free and deterministic. No sockets, no room, no `rooms-server`, no
`io`. The engine is a reducer: state plus an action gives new state plus events.

**Seats are not yours to invent.** `@wolffm/rooms-protocol@0.38.109` is
dependency-free, socket-free, and already models exactly what a draft pod needs
— read `seats.d.ts` before writing a line. Its own header says *"in a draft the
pack passes left, then right, then left again"*; it gives you `SeatId` **as**
the ordering, seats sticky across reconnect (which is D11's "a mid-draft refresh
must not vacate a seat for even one tick", solved), `SeatOccupant` with
`kind: 'bot'`, `padWithBots` with deterministic positional `bot:<n>` ids, humans
evicting bots, and `capacity` for the pod. Consume it. Re-deriving a seat model
here is how the two diverge.

1. Depend on `@wolffm/rooms-protocol` **only**. Importing `@wolffm/rooms-server`
   or `socket.io` in this package fails the lane.
2. Pack building from a cube pool plus a recipe: shuffle, deal `NumPacks ×
   NumPlayers` packs of the recipe's size, honour `Singleton`. A **seeded** RNG
   you own — `Math.random` fails the lane, because replay is the whole test
   strategy.
3. The pick/pass loop: pass direction alternates by pack round (left, right,
   left), a pick is validated against the actual pack, out-of-turn and duplicate
   picks are rejected as values, and the round advances when every pack is
   empty.
4. The heuristic bot: colour commitment plus curve, deterministic under the
   seed, picking for any `kind: 'bot'` seat.
5. The wire shape, as Zod in `packages/shared` — the envelope below is
   **settled** and lane C is rendering fixtures against it, so it may be
   extended but not reshaped:
   - `DraftId`, `seq` (monotonic, matching `CoreRoomState.lastEventSeq`'s
     contract), `packNumber`, `pickNumber`, `seats`, and **per-seat visibility**:
     the pack a seat can see, its own picked pool, and nothing of anyone else's.
   - The hidden-information split is the point. A spectator payload must never
     carry another seat's pool.
6. Done when: an 8-seat, 3-pack draft runs to completion in a test; **the same
   seed twice produces a byte-identical pick log**; a pick out of turn is
   rejected without throwing; and a test asserts over a **whole serialised
   payload** that no seat's view contains another seat's picks.

## §C — The draft UI, on fixtures

React, in `apps/ui`, rendering a draft from committed JSON fixtures. **No
server, no socket, no room chrome** — do not import `@wolffm/watchparty-ui` or
`@wolffm/rooms-server`, and do not build the surrounding room; watchparty's room
UI is not integrated this wave and this lane is the canvas-slot interior only.

1. The pack view (cards fanned for picking), the picked pool, pack/pick counters,
   and whose turn it is by seat.
2. Card rendering is **ours**: name, cost, type, text, P/T drawn as our own
   layout. **No card images** (D13), and **no WotC marks** — no mana symbols,
   set symbols, tap symbol, or card frames. Draw our own pips.
3. Write the fixtures yourself, against §B.5's envelope. They are the lane's
   contract with B.
4. Done when: `pnpm --filter @hadoku/ui dev` renders a full pack from a fixture
   and a pick updates the view; **and `apps/ui`'s fixtures parse under lane B's
   Zod schema** — one command, which the manager runs after B has landed. A
   fixture that does not validate is a lane C failure, not a B failure.

## §D — PR-4 spike: does Forge start headless as a server?

PR-4 is unblocked and now the bigger programme. Wave 1 proved the *engine* runs
headless; this asks the next question, cheaply. `Main.java:111` is
`case "server": System.out.println("Dedicated server mode.\nNot implemented.");`
— but `case "sim":` next to it *is* implemented (`SimulateMatch.java`, 404
lines) and is the working precedent for a headless entry point.

1. **Write no Java into `forge/`.** The fork does not exist (D2, O1). Everything
   goes in an overlay under `scripts/spike/`, the pattern Wave 1 lane B proved.
2. Get `SimulateMatch` to run against the stock tree and capture its output —
   that establishes headless-entry viability with something already implemented.
3. Map the 62-method `ProtocolMethod` enum against what a browser draft/play
   client actually needs: which methods are required, which are desktop-only,
   and which carry a `FSerializableFunction` (the board flags `getChoices`/`one`
   as passing a *function* — settle whether that is a real wire problem).
4. Report jUPnP: `FServerManager` imports `org.jupnp`. Say whether it can be
   disabled by config or needs a code change in the fork.
5. Done when: `docs/spikes/headless-server.md` carries the reproduction
   commands, `SimulateMatch`'s actual output, the 62-method table with a
   required/not-required column and a count, a verdict on
   `FSerializableFunction`, and the jUPnP answer. **`forge/` is byte-for-byte
   pristine afterwards** — the manager checks with `git -C forge status` and a
   HEAD comparison.
