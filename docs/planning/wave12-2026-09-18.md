# Wave 12 — the loop closes: draft a pool, build a deck, play it; and the eras the goal actually needs

Protocol: `docs/handoff/w12.md` carries it. One manager, one sub-agent per lane,
all parallel, no shared files. Implementers commit and stop; the manager
verifies from artifacts, lands lane by lane, and confirms the deploy.

## Settled — do not re-open in any lane

- **No money, ever** (`docs/LICENSING.md`). No sales, subs, ads, donations.
- **The friend gate stays.** `/cardtable/*` is friend-tier at the edge. No
  public or anonymous tier, not for any lane's convenience.
- **Card art lives on `cdn.hadoku.me`; image bytes never enter the repo** (D15,
  operator 2026-09-15). Our own origin never serves an image; every art URL is
  absolute. `scripts/d13-gate.sh` fails CI on a relative one.
- **Art is a lookup, not a URL** — `art-manifest.json` maps `scryfallId →
  {source, key}`. The operator expects to re-source the art, so repointing a
  card must stay a one-line data edit.
- **No WotC trademarks in our chrome.** Draw our own pips; `{T}` is the word TAP.
- **Never build in the vendored `forge/` tree** (D2). It must stay pristine.
  The production jar is built off-tree — `docs/FORGE_JAR.md`.
- **Never `git submodule deinit` in a worktree.** It unregisters `forge` in the
  deploy tree, which is the checkout PM2 serves from.
- **D12 clean-room firewall**: an agent that has read `forge/` or
  `docs/FORGE_ANALYSIS.md` may not implement a clean-room room module. No lane
  here requires it; if one thinks it does, it stops and reports.
- **Reimplement draft in TS, not Forge's `limited/`** (O2, 2026-09-14).
- **One JVM per match** (O3) — Forge's `FServerManager` is a per-JVM singleton.

## §A — The four missing Standard eras (PR-5)

The operator's goal is *"to recreate standard formats from years past"*, and
their window was **"between New Phyrexia block and Return to Ravnica block"** —
that is **2011-05-13 → 2012-10-05**. Checked against Forge's own rotation table
(`packages/carddata/src/formats/standard-history.generated.ts`), the collections
in `decks/` cover that window far less well than the deck count suggests:

| effective | era | decks we have |
| --- | --- | --- |
| 2011-02-04 | Scars/Zendikar | PT Paris 2011 (8) — **outside the window, pre-NPH** |
| **2011-05-13** | **New Phyrexia** | **none** |
| **2011-07-15** | **Magic 2012** | **none** |
| 2011-09-30 | Innistrad | GP Hiroshima (1) + Worlds (8) |
| 2012-02-03 | Dark Ascension | PT Dark Ascension (8) |
| **2012-05-04** | **Avacyn Restored** | **none** |
| **2012-07-13** | **Magic 2013** | **none** |

So 25 decks sit in **two** of the window's six eras, and the largest single
collection is not in the window at all. Do **not** delete PT Paris — the
operator has played with those decks and Caw-Blade is why the July 2011 bans
happened. It is context for the window, and this lane simply stops it from being
mistaken for coverage.

1. Add **four** collections, one per missing era, **~5 decks each**, real
   tournament decklists with the player named, in the shape the existing
   directories use (`decks/standard-<date>-<event>/N-player-archetype.dck`).
2. **All five colours represented at least once within each era's set**, the
   same rule the operator set for the earlier collections. Mono or two-colour
   with the scarce colour is fine — the operator accepted Solar Flare for black.
3. Add each era's date to `FIXTURE_DATES` in `build-pool-fixture.ts` and
   regenerate. The corpus is gitignored and **absent from a worktree**, so point
   at the main checkout:
   ```sh
   node --max-old-space-size=6144 packages/deck/src/library/build-pool-fixture.ts \
     --cards=/home/hadoku/repos/hadoku-cardtable/packages/carddata/data/cards.jsonl
   ```
   It **reads** the corpus and writes nothing near it.
4. Every deck must be **legal in its own era's frozen pool**, proven by
   `library.test.ts` against the generated fixture, not by inspection. A deck
   that will not validate is a deck sourced wrong — fix the list, never the
   validator, and never widen the pool to admit it.
5. Watch for the trap that already bit once: a pool freezes card **names**, and
   double-faced cards need both the full name and the front face
   (`poolNameKeys`). Innistrad-block eras are exactly where this bites.
6. Done when: four new collections exist; `pnpm test` passes with every new deck
   validated against its own era's generated pool; the five-colour rule holds
   per era and the closing note states the archetype and colours of each deck;
   and reverting any one new `.dck` to an illegal list **fails** a named test.

## §B — Build and play the deck you drafted (PR-2 × PR-4)

**This is the product's missing middle.** A friend can draft a pod (proven, Wave
10) and can play a prebuilt Standard deck (proven, Wave 11) — but `DeckScreen`
renders the words *"Not built yet"* and a button back to the draft, so **the 45
cards you just drafted cannot be played**. Draft and play are two products that
do not meet.

The server half already exists and is not this lane's to build: the gate's
`{ kind: "draft", draftId }` arm validates a deck against **the caller's own
drafted pool** and hands Forge the same bytes it checked
(`apps/server/src/http/README.md`). This lane is the UI that finally calls it.

1. `DeckScreen` shows the drafted pool and lets the drafter build from it.
2. **Basic lands.** A 45-card pool is not a legal deck; limited decks are 40
   cards minimum and the lands are added, not drafted. The screen must let the
   player add basics, and the count must be part of what is validated.
3. Starting a match goes through the **existing** gate arm. Do not add a second
   path to Forge, and do not weaken the check: an illegal build is refused with
   **the offending card named**, and the refusal is server-side.
4. The deck the gate validated must be the deck Forge plays — Wave 11 lane D
   made those the same bytes, and this lane must not reintroduce a second
   reader.
5. Done when: from a completed draft, a browser builds a deck and starts a match
   from `#/deck/<draftId>`; an illegal build is refused with the card named and
   a test proves the refusal is server-side (it still refuses when the client
   check is bypassed); and the closing note says whether a drafted deck and a
   constructed deck now reach Forge by one path or two, **with the line numbers**.

## §C — The JVM's footprint (PR-4 hygiene)

`stageRunDir` (`host.ts:274`) `rmSync`s a run directory *before* creating it and
nothing removes it after the match ends. Every match gets a fresh random id, so
`/tmp/cardtable-play/` grows without bound: **78 directories / 16 MB** from a
single day of testing, ~205 KB a match. `/tmp` is **tmpfs**, so this is RAM.

It is low severity and it is not nothing: 13 G is free and a reboot clears it,
which is exactly the profile of a leak that is invisible until the day it isn't.

1. Remove a match's run directory when the match is over, on the path that
   already exists for that (`stop()` / the over-grace). A match that crashed is
   the interesting case — `bridge.stderr.txt` under the run dir is the only
   record of *why*, and Wave 11's crash test reads it. **Do not delete the
   evidence a failed match leaves**; decide what to keep, keep it deliberately,
   and say so.
2. Sweep what is already there on boot, or say why not. 78 directories exist on
   this host right now.
3. Do not change the JVM-per-match decision (O3) or the warm-spare behaviour;
   this lane is the footprint, not the lifecycle.
4. Done when: a test proves a finished match's directory is gone and a crashed
   match's diagnostics are still reachable; `jvm.test.ts` passes against the
   installed jar with `jvmsLeft: []`; and the closing note gives the directory
   count before and after a run of the suite.

## §D — Room chrome, settled either way (PR-3 / PR-6)

The operator has asked twice: *"we gotta connect this to my room and network
system. watchparty has already done all the work for us so it should be no
problem."* It has not happened, and the reason is recorded in **D17**:
`@wolffm/watchparty-ui@0.38.115` exports only `createWatchpartyRouter`, `mount`
and `unmount`, and ships **zero** `.d.ts`. Re-checked 2026-09-18 on the
registry: still no `types` field at 0.38.115.

So the honest question is not "integrate it" but **"can it be integrated, and if
not, what exactly do we need from watchparty?"** — and the lane is done either
way. What is not acceptable is a third wave in which this is neither done nor
decided.

1. Read what the package **actually ships** (unpack the tarball; do not infer
   from its README). Say what `mount`/`unmount` do, what they expect to own, and
   whether room chrome can be used **without** handing them our whole app — we
   are a standalone app that imports their room UI (D17), not a payload inside
   their router.
2. If it can be used: prove it with the smallest possible spike, **outside
   `apps/ui`** (this lane does not own `apps/ui`). Report to the manager what
   the integration would cost and which files it would need.
3. If it cannot: write the request to watchparty in `docs/requests/`, in the
   shape the earlier ones use — the precise export we need, why our own room
   layer is not a substitute, and what we will do with it. Name a version we can
   consume.
4. `packages/room-ask` still **has no consumer** (board, `watch`). Say plainly
   whether this work gives it one or whether it should be handed to watchparty.
   A package with no consumer and no owner is a liability, not an asset.
5. Done when: a spike doc in `docs/spikes/` states what the package exports,
   from the tarball; **and either** a working spike with a costed integration
   plan **or** a request doc naming the exact export and version; and the
   closing note answers the `room-ask` question in one sentence either way.
