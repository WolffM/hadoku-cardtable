## Why

`templates/game` is a September starter. It pins watchparty's `rooms-server`/`rooms-protocol` 0.39.4 (live is
0.45.x+) and its own hand-written rooms, so a game hydrated from it today gets none of phases 1–6. The plan's last
fleet step is to **rebuild `templates/game` on the packages**. The operator wants to build their next game from it.

## Settled

- **The template is a standalone repo built on the published MIT packages:**
  - `@hadoku/service-kernel` (already published);
  - `game-server`: the kernel, `RoomLobby` with `RoomTypeHooks` (`plainRoomType`), and the relay runtime;
  - `game-ui`: the room view and the bundle slot / relay channel;
  - `ui-shell`;
  - `platform-wire` and `host-wire`;
  - `room-ask`, if `game-server` needs it.

  It does **not** live under cardtable's `games/`. That path is for games that ship inside cardtable's own site;
  w117 §5 covers that case, and the template's README points to it.
- **Publishing.** Generalise `publish-kernel.yml` into one workflow over a list of packages. Each run uses the same
  steps it does today: the manifest step, `next-version`, build, pack listing, publishing to GitHub Packages as
  `@wolffm/<name>`, and the npmjs half as a dry run behind a per-package `NPMJS_<NAME>` variable.
  - Moving service-kernel's own scripts into a shared one is fine **only if** service-kernel's next publish still
    produces the same tarball file list. Prove that by diffing the `pnpm pack` listing before and after.
  - Published packages must not import the workspace's GPL packages. The layer ratchet already says MIT; prove the
    tarballs by installing them in a scratch dir outside the workspace.
- **npmjs first publish is a human step**: it needs a pty and an OTP. You don't do it. Write
  `docs/requests/<date>-platform-packages-npmjs.md` in hadoku_site, in the shape of the kernel's request. Until the
  operator does the first publish, the template installs from GitHub Packages. Check that this works with the
  template's `setup-pnpm` read token, and say so in the README.
- **The template's game is a toy and a real one.** Two seats take turns on a shared counter, or something just as
  small. That's enough to show:
  - a room type registered through `RoomTypeHooks`;
  - a match on the relay runtime (the leader's browser is authoritative, as bomberman's is);
  - a result through `over`;
  - a rematch in the same room.

  No card kit and no Magic.
- **The old room code is deleted** (`apps/server/src/rooms.ts`, the `rooms-server` and `rooms-protocol` pins, and its
  tests), not left beside the new code. Edge auth and the tier floor stay on service-kernel, as they are now; keep
  `tier-floor.test.ts`'s refusal.
- No version edits in cardtable. No AI attribution. Never `git stash`. Never `pnpm install` in the cardtable
  worktree. Never `/cutrelease` or `release.yml`. Never write under `~/srv` or `~/srv-data`.
