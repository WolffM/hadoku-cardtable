## Why

From the operator's Playtest 12 (ledger AB2–AB6, AB9, AB11, AB13) on `14ecc8e`, match `m-45b21c9f6cbd`:

- **AB11 (Z4's THIRD ask).** *"decision popups should not display if it's being automated … the delays
  should not impact whether a decision is displayed."* Production's log for the match: Bitterblossom's
  ask answered 17:27:55.888Z, `auto-paid {1}{B}` at .894, the caster's priority `auto-passed` at .904. The
  server answered both windows within 16 ms, and the seat still drew the Pay Mana Cost pop-up and a
  "Resolve?" pop-up. Forge sends a window as TWO frames, `showPromptMessage` then `updateButtons`;
  `match.ts:1337-1395` forwards the prompt when it arrives and decides (`maybeAutoPay`,
  `maybeAutoPass`, `maybeConfirmChosenCost`) on the buttons frame, so every auto-answered window is drawn
  for the frames in between. Z4's earlier fix (`158cbd3`) moved `maybeAutoPay` ahead of the forward but it
  decides against the PREVIOUS window's buttons there, so it rarely fires at prompt time.
- **AB9.** The opponent's board flashes highlighted as End Turn skips declare attackers: the
  declare-attackers window reaches the UI (`attackDefenders`, `live/match.ts:1771`) before the server
  auto-passes it. Same cause.
- **AB3.** "Waiting for Hadoku" flashes after both seats kept: a state drawn for the frames between
  Forge's mulligan end and the first priority prompt. Same family; confirm it is, from frames.
- **AB13.** *"might be worth it to capture some telemetry from games so we can more easily repro."* The
  server log carries `auto-passed`/`auto-paid`/`ask-*` per match (`match.ts:683-708`, `deps.log`) but not
  which prompts it forwarded or withheld; `CARDTABLE_PLAY_DUMP` (`apps/server/src/play/scenario.ts`) is a
  test-harness facility, nothing like it runs in production.
- **AB6 (AA4's second ask).** *"release the card to play it. it immediately appears on the board (bad),
  and the phantom cardback is still attached to the cursor (also bad)."* `presence.ts:11`: a message goes
  out on `pointermove` only, throttled to `PRESENCE_SEND_MS`, so the release is announced when the pointer
  next moves. The hand-off flight (`handoff()`, `presence.ts:306`) needs `motion` on.
- **AB4 (AA5's second ask).** The cursor drifts at the board/board and board/hand seams: `spotOf` /
  `placeSpot` (`presence.ts:106,130`) are zone-relative, and between zones the last zone's box scales the
  pointer until it crosses.
- **AB5.** *"when the screen is resized to be very vertical, the cards get smaller so they can fit in the
  hand in a two stack. however, the opponent still sees the cards depicted in a row."* Their hand is drawn
  from the count alone; the row count their window produced (`board.css:184,1005`, the two-row lane) is
  not on the wire (`PresenceSchema`, `packages/shared/src/presence.ts:63`: `pointer`, `held`, `from`).
- **AB2 (Z2's THIRD ask).** *"'Return 1 card(s)…' → 'Return 0 card(s)…' is awkward. remove the 'auto'
  button, grey out OK until the criteria has been met."* The pop-up draws each of Forge's prompt texts as
  they arrive and passes Forge's bar through; OK is gated on `bar.enable1` already
  (`LiveBoard.tsx:2271`), `button2` is drawn whenever `decisionCancel` (`:2272`).

## Settled — do not re-open in any lane

- **The server decides before the seat sees.** A window the server will answer is never drawn, with or
  without a pace delay: the delay is a wait on the ANSWER, not a chance to show the question (operator,
  three times). Hold a `showPromptMessage` until its `updateButtons` arrives (Forge sends them
  back-to-back; a 250 ms safety flush forwards a prompt whose buttons never come), decide once on the
  pair, and forward both or neither. A window the server will not answer is forwarded exactly as today.
- **Telemetry is the server's structured log, not a new store:** `prompt-forwarded` and
  `prompt-withheld` events with the window kind and the decision, and a per-match ring buffer of the last
  N frames each way, written to `$CARDTABLE_PLAY_WORK_DIR/<matchId>/frames.jsonl` on match end (N and the
  retention are the lane's call, with the number in the note). No new endpoint, no client-side store this
  wave.
- **Presence sends on release**, immediately, not on the next move; the hand-off flight starts from the
  back's last spot the moment the card's own tile exists; the back goes on release.
- **Seams:** the pointer is mapped in BOARD coordinates with the zone as a hint, never scaled by a zone
  the pointer has left; a pointer in a gap between zones is placed in the gap.
- **Their hand draws as they see it:** the row count (1 or 2) their layout produced travels on the
  presence message and their hand is laid out with it; nothing else about their hand is revealed.
- **The mulligan pop-up:** the FIRST text Forge sends for the pick stays for the whole pick ("Return N
  card(s) to the bottom of your library", N = the count to return); no second button; OK greyed until
  Forge enables it. No text of ours.
- Theme tokens only, no explanatory UI text, delete what you replace (`made dead / deleted: …` in each

- Proof on the claws: `git push origin HEAD:refs/heads/verify/w55-<lane>` then
