## §0 — The operator's ask, and what it actually costs

> *"why do we have 'start a pod' as a button but we also have 'game type'
> selector at the top? i think just completely get rid of the 'start a pod'
> button and draft pod section. only one entrypoint. drafts/constructed
> should just be treated as rooms."*

They are right about the product: two doors to one idea is the confusion, and
the room list already offers `draft` as a game type. **But deleting the button
is the 10%.** The tracker checked before planning, and the two things are not
the same object today:

| | lobby room | draft pod |
| --- | --- | --- |
| id | server-minted `r-<hex>` | **client**-minted `adjective-noun-suffix` (`mintDraftId`, `route.ts:158`) |
| created by | `POST /api/rooms` → `lobby.create`, persisted to disk | the socket, on demand: `rooms.open(msg.draftId)` (`room/socket.ts:248`) |
| carries | name, password, members, leader, `clientMode`, `gameType` | seats, packs, picks — and nothing else |
| route | `#/room/<id>` → `ConstructedScreen` | `#/draft/<draftId>` → `PodScreen` |

**And the room screen has no draft branch at all.** Grepping
`ConstructedScreen.tsx` for `gameType` / `'draft'` returns nothing — so a room
created with game type `draft` today lands its members on the **constructed
deck picker**. The game-type selector already promises something the room
screen does not deliver; that is the actual defect behind the operator's
complaint, and deleting the pod button without fixing it would remove the only
working way to draft.

## §1 — Settled, do not re-open

- **One front door.** The room list is it. When this wave lands there is no
  "Start a pod" button and no draft-pods section.
- **A draft room is a room**: it has a name, a password if the creator wants
  one, members, and a leader, exactly like a constructed room.
- **Do not break drafting to achieve tidiness.** If the unification cannot be
  finished, the pod entry point STAYS and the wave reports that — a tidy front
  page that cannot start a draft is worse than two doors.
- The canvas rules, the no-prose rule and the hidden-information rule are
  unchanged and outrank any lane's preference.

## §A — one id, one room

Make the lobby room the container a draft runs in.

1. A room created with `gameType: 'draft'` **is** the pod: the draft engine
   opens against the room's own id, so `rooms.open(<roomId>)` and
   `lobby.get(<roomId>)` describe one thing. The client stops minting ids.
2. Decide and state what a draft room's **seat count** is — the pod is eight
   seats and bots fill what nobody takes; a lobby room has members. Reconcile
   those two ideas explicitly rather than letting one silently win.
3. **A draft in progress must not be destroyed by the lobby's own rules.**
   `ROOM_IDLE_MS` (12 h) reaps idle rooms, and `matchId` is cleared on restore.
   Draft state is in memory; say what happens to a draft when the server
   restarts mid-pod, and make the answer honest in the UI rather than a
   silent empty table.

Done when: a `draft` room's id is the only id in play, a pod opened from it
seats its members, the seat-count question is answered in writing, and nothing
in the lobby reaps a live draft.

## §B — the room screen knows what game it is

`ConstructedScreen` gains the branch it never had: `gameType: 'draft'` renders
the pod (today's `PodScreen` content), `constructed-1v1` renders the table.
Both inside the same room chrome, with the same members list and the same
leader controls.

Done when: entering a draft room drafts, entering a constructed room plays,
and neither shows the other's furniture.

## §C — one front door

1. **Delete the draft-pods section**: the "Start a pod" button and the
   "Join a pod or a match" box.
2. **Keep what the join box did that the room list does not.** It accepted a
   pasted invite link or a bare id — that is how a friend joins from a link.
   The room list must answer the same need (an invite link opens the room
   directly, which `#/room/<id>` already does) — verify it does before
   deleting the box, and if it does not, that gap is this lane's to close.
3. `mintDraftId` and the `#/draft/<id>` route go once nothing needs them —
   including the old links. State what happens to a link someone already has.

Done when: the front page offers exactly one way to start a game, an invite
link still works, and no dead route remains.

## §D — the draft proof, through the front door

`e2e/draft.spec.ts` is the only end-to-end proof that drafting works, and it
drives `start-pod` and `join-id` — both of which this wave deletes. **Rewrite
it through the room list**: create a draft room, a second friend joins it from
the room list, and the pod runs exactly as it does today.

**This lane is the wave's safety net.** If it cannot be made to pass through
the new door, the unification is not finished — say so, and §C's deletion does
not land.

Done when: two friends draft one pod having started from the room list only,
with the same assertions the current spec makes.
