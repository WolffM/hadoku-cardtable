# Wave 101 — platform phase 5, part 1: the match host's seams (runtime, hosting, the game adapter, the bundle contract)

Protocol: `docs/handoff/w101.md`. One manager, one Sonnet sub-agent per lane, all lanes in parallel, no shared files.
Implementers leave changes uncommitted and stop. The manager verifies from artifacts and lands lane by lane. A lane
counts as landed once PPE's `/health` carries it, or, for the watchparty lane, once the package is published and
cardtable's lockfile can take it.

**Why:** phase 5 of the platform plan (artifact Jm5BXZj9xLPnpMGDwLSTKu; v2 at
`~/.cache/cardtable-manager/handoff-2026-11-07/platform-plan-v2.html`, "Phase 5 · Match host and the bundle slot")
is where a game that isn't Magic gets somewhere to run. The operator, 2026-11-11: *"i'm looking forward to using this
system to build a new game once this is ready."* Today every match is a Forge JVM: `play/local-jvm.ts` (1,235
lines), `play/host.ts` (1,359), the claws' signed agent protocol (`play/remote/wire.ts`, whose `LaunchSpec` is
`xmxMb`/`main`/`jvmFlags`/`forgePreferences`), and `play/match.ts` (5,245 lines, `class Match` at `:1269-4961`). This
wave cuts the seams the plan sketches:
- L1, `EngineRuntime`: how a process starts;
- L2, hosting without Forge's types;
- L3, `GameAdapter` and `GameSession`: what a game supplies;
- the bundle contract's optional `match` and `channel` fields.

It does all of that **without changing what any match does**.

## §R — L1 runtime and L2 hosting (long pole)

The plan's sketch:

```ts
// L1 process: today jvm-transport.ts, local-jvm.ts, remote/, apps/agent
interface EngineRuntime { artifacts: Record<string, string>; argv(dir: string, size: { memoryMb: number }): string[];
  overheadMb: number; perProcess: number; health?(dir: string): { recycle: boolean } }
// L2 hosting: today host.ts minus its Forge types
interface Durable { epoch: string; owners: (string | null)[]; checkpoint?: { turn: number; state: string } | null }
```

It is a starting point, not a final API. Every method must map to code that exists today.

1. **`EngineRuntime`.** `local-jvm.ts` splits:
   - the generic process hosting moves to a platform file: run dirs (`stageRunDir`), fifos and I/O (`makeFifos`,
     `openJvmIo`), `writeFileAtomic` (or the kernel's, if it is the same; it moved in w99-R), the launch record and
     crash records;
   - the Forge half becomes the first `EngineRuntime` and stays `magic`: `BRIDGE_JVM_FLAGS`, `FORGE_PREFERENCES`,
     `bridgeLaunch`, `bridgeVersion`, the Flat-MC config and `JVM_HEAP_MB`;
   - `jvm-transport.ts`'s `JvmLauncher`/`JvmTransport` lose "Jvm" from their meaning; rename them only if every
     importer is on R's row.
2. **The launch spec is runtime-typed and additive.**
   - `LaunchSpec` gains `runtime: { kind: 'jvm'; … }`, carrying what `xmxMb`/`main`/`jvmFlags`/`forgePreferences`
     carry today. The old fields stay on the wire until w103's agent rollout.
   - The agent reads the runtime when present, and the old fields otherwise.
   - Tests over the real signer and verifier: an old-shape spec and a new-shape spec each launch on the new agent,
     and the new server's spec parses on an agent built from 170e6826c's `apps/agent` (check that out into a scratch
     dir; don't hand-copy).
3. **`remote/wire.ts` moves to a package**, as the plan says:
   - a new MIT package under `packages/`; name it for what it is, for example `packages/host-wire`;
   - every importer is rewritten in the same commit;
   - `apps/agent` bundles it. `scripts/agent/deploy.sh` must follow the move: its `build` imports `wire.ts` by path,
     and its version stamp diffs `apps/server/src/play/remote`. Prove it with `deploy.sh build <scratch dir>` under
     `AGENT_KEY_FILE` set to a throwaway key from `deploy.sh keygen <scratch dir>`. **`build` only, never
     `install`**: `install` touches a claw;
   - the relay protocol (`RELAY_PROTOCOL`, the signing) comes along unchanged.
4. **L2.**
   - If w100's item 3.2 landed, `host.ts` is already generic over its line and command types. Take `Durable` (epoch,
     owners) in, as the record `jvm.json` already is.

     22 importers unchanged, and the platform importers (`start-queue.ts`, `placement/*`, `remote/*`) gaining no Magic

## §M — `match.ts`: pure moves, and the L3 interfaces

The plan's sketch (a starting point):

```ts
interface GameAdapter<Spec, Line, Cmd, Frame, Input> {
  seats(spec: Spec): { ai: boolean; name: string }[];
  classify(l: Line): { t: 'ready' } | { t: 'seat'; seat: number; raw: unknown } | { t: 'over'; placements: number[] }
    | { t: 'checkpoint'; cp: Checkpoint } | { t: 'fatal'; why: string } | { t: 'info' };
  session(out: { toSeat(seat: number, f: Frame): void; toWatchers(f: Frame): void; command(c: Cmd): void }): GameSession<Cmd, Input, Frame>;
  restoreSpec(spec: Spec, cp: Checkpoint): Spec; concede(seat: number): Cmd; notice(text: string): Frame; }
interface GameSession<Cmd, Input, Frame> { ingest(seat: number, raw: unknown): …; … }
```

1. **The interfaces**, in a new platform file (`play/game-adapter.ts`).
   - Derive every method from what `class Match` does today. Read the class and map each method to the member(s) it
     stands for (`file:line`).
   - The non-Forge test bridge (`play/fixtures/fake-bridge.mjs`) already drives the host pool. Write a toy adapter
     for it in a test, which shows a non-Forge game fits the interfaces: compile-level plus one unit test that
     classifies its lines. Not a runtime: that's w103.
   - **Land this first.**
2. **Pure moves out of `match.ts`**, as rename-only commits:
   - the outcome helpers (`:257-332`: `MatchStatus`, `GameOutcome`, `OutcomeFacts`, `gameOutcome`,
     `winnerSeatFromLosers`) go to a platform file. They are generic, and two platform files used them before w99;
   - the registry (`:4961-5245`: `restoredSpec`, `MatchRegistry`, `ResumeFrom`, `EndedMatch`, `Restored`,
     `RegistryDeps`, `createMatchRegistry`) goes to its own file under `play/match/`. Its layer is whatever it really
     imports;
   - Forge's frame helpers (`:903-1268`: the window shapes, `promptShape`/`buttonsShape`, the reveal helpers,
     `forgeAct` and the act sets) go to magic files under `play/match/`.
   - **Every importer is rewritten in the same commit; no shims.** An importer on a w100 path (`plugins/*`,
     `parked.ts`) is the one exception: leave that export where it is, and say so.
3. **The member map**, for w102: a table in `docs/planning/w102-match-split-map.md`, one row per member of
   `class Match`, giving its line range, **shell** or **session**, and why. "Shell" means seats, grace, rejoin,
   watchers, per-seat emit, parking, recording hooks, the activity window, concede timing. "Session" means asks,
   windows, auto-pass, holds, Forge acts.
   - Count both. Name every member that is both, because those are w102's real work.
   - This is a lane deliverable, checked by the manager against the file; it is w102's brief.
4. **Done when:**
   - `pnpm run check` exits 0;
   - each move commit is rename-only (`git show -M --stat`, and the manager's line-match check as in w99-L);

## §S — the bundle contract's `match` and `channel` (watchparty)

The plan's sketch:

```ts
interface GameBundleContext {
  match?: { id: string; seat: number | null; seats: SeatInfo[] }; // a null seat is a watcher
  channel?: MatchChannel; // talk through the host's socket, for a game with no server of its own
}
```

1. **In `packages/rooms-protocol/src/game-bundle.ts`:**
   - `match` and `channel` are optional;
   - `SeatInfo` is the seat's index, its userId or null for AI or empty, and its display name;
   - `MatchChannel` is per-seat and ordered: `send(msg)`, `on(handler) → unsubscribe`, and `close` semantics. Write
     its contract in the doc comment: ordering, at-most-once or at-least-once (pick one and say why), and what a
     watcher may send (nothing);
   - **everything optional**, so every existing bundle and host keeps working.
2. **A reference in-memory `MatchChannel` pair** (for tests, exported) and a contract test:
   - two seats exchange messages in order;
   - a watcher receives but cannot send;
   - close ends both sides.
3. **Compatibility:** a test that mounts a bundle written against today's context (no `match`, no `channel`) under the
   new types, and one that mounts a bundle that reads `match` when given it.
4. Land the watchparty way (its AGENTS.md), with neutral commit messages. Publish through its `publish-packages`
   workflow (rooms-* ship in lockstep), then hand the version to the manager. The cardtable side is only the lockfile
   bump (the manager runs `update-wolffm`) and `pnpm -r typecheck` on it.
5. **Done when:**
   - watchparty CI and Publish Packages are green, and the version is in the note;
   - cardtable typechecks on it;
   - each test goes red against a mutation: the channel reorders, or a watcher's `send` delivers (counts);
   - nothing in watchparty's own host changes behaviour (its e2e as its CI runs it).
