## §A — The table's format belongs to the leader (item 1, server half)

The room already HAS a leader: `lobby.ts:574` sets `leader: caller.id` at
create, `RoomView` carries both `creator` and `leader` (`lobby.ts:120-125`),
and `setGameType` is already leader-gated with a `not-leader` reason
(`lobby.ts:646-660`). So this lane adds no leadership; it moves a setting under
the one that exists.

The bug underneath the request: **the format is per-seat, not per-table.**
`PUT /api/tables/rooms/:roomId/deck` takes `{ deck, rules }` from each caller
and stores each player's own rules (`routes.ts:401-425`), and `startFromRoom`
only ever checks each deck against its OWN rules (`routes.ts:551-557`). Two
players can load decks legal in two different Standard pools and the match
starts anyway. "Matched" is not a mode to invent — it is a property the table
never had.

A second, smaller gap that blocks §B: **no client can tell that it is the
leader.** `RoomView.leader` is a hashed ParticipantId, `RoomMember` carries
`id` and `name`, and nothing tells a caller which id is theirs — the header of
`ConstructedScreen.tsx:37-44` says so in words. The table view already computes
`you` per player (`routes.ts:355`), so the pattern exists; it does not compute
`you.leader`.

1. Add the room's rules to the room's own app blob: a format id, defaulting to
   the NEWEST pool, not `formats[0]`. `library.formats` is documented "in date
   order, oldest first" (`http/library.ts:63`), so the default is the last
   element. Persist it through the same codec that carries `leader` and
   `gameType` (`lobby.ts:305-322`, `:370-390`), and restore it — a room that
   came back on a different pool from the one its players loaded decks against
   is the bug this field exists to prevent.
2. A leader-gated setter, in the shape `setGameType` already has: refuse with
   `not-leader` for anyone else, and CLEAR every player's readiness and deck
   verdict when the pool changes, for the reason a new deck un-readies you
   (`routes.ts:418`) — what they readied with is not legal in what the table is
   now.
3. `PUT .../deck` stops taking `rules` from the caller. The room's pool is the
   rules, for both seats. Decide and write down which of these the body does:
   reject a body that carries `rules` (400), or accept and ignore it. Prefer
   REJECT — `http/rooms.ts`'s PATCH already refuses a field it will not honour
   rather than accepting and ignoring (`lobby.ts:88-92` records why).
4. `startFromRoom` checks both decks against the ROOM's pool. Keep the existing
   refusal shape and its privacy rule: naming the other player's offending card
   would report their pool to whoever pressed the button (`routes.ts:549-552`).
5. Add `you.leader` to the table view beside the `you.player` already there, and
   a caller-scoped `you` to the room view that `http/rooms.ts` serialises —
   this also closes wave 23's known gap, where a reload while ready relabels
   the Ready button and cannot stand down in one click.
6. Done when: `apps/server` tests pass, and each of these is a NAMED test that
   fails when the change is reverted — a non-leader's setter call answered
   `not-leader`; a pool change clearing both readiness flags; a `PUT deck`
   carrying `rules` refused; a start refused when one deck is illegal in the
   room's pool while legal in another; `you.leader` true for exactly one
   member. Report the count of tests added and the reverted-FAILS / restored-
   PASSES pair for at least one of them.
