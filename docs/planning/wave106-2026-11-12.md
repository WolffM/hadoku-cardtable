## The shared contracts

**N's bomberman-over-channel protocol**, written by N in bomberman's `packages/protocol` and pinned in the
manager's notes at N's first report. It maps bomberman's existing host-authoritative messages (`docs/NETCODE.md`:
inputs up to the host, snapshots down at 30 Hz, the host's result) onto `MatchChannel`'s opaque messages. The
match's end is `{ t: 'over', winners: number[] }` (seat numbers) through the channel, which cardtable's
`RelayMatch` reads (w105-C's list).

**M's game-clients context** (`apps/ui/src/rooms/game-clients.tsx`, platform): the platform room shell provides
the injected clients, and a game's `GameRoomUi` reads them from the context instead of closing over
`RoomTableScreen`'s props. w104b's list of what Magic's setup needs is the input: `client: TablesClient`,
`feed: RoomFeed`, `rooms?: RoomsClient`, `streamFetch?: Fetch`, `rand: () => number`,
`makeTransport?: () => DraftTransport`, `deckRecords: () => Promise<DeckRecords>`, `myDecks?: MyDecksClient`,
plus the route's `roomId` and `tableId`. The context's type is generic (platform). Magic's concrete client types
fill it from the Magic side, so the platform file names no Magic type.
