# Wave 119: one room model across the sites (stage 1 of bomberman's move home)

Protocol: `docs/handoff/w119.md` carries it. One manager, one sub-agent per lane, all parallel, no shared files.
Implementers commit and stop. The manager verifies each lane from its artifacts, lands lane by lane, and calls a lane
landed only when PPE carries it (and, for lane P, when the package is published).

## Why

On 2026-11-16 the operator stopped the bomberman live check at its first step:
- **1a:** a new bomberman room said "no such room". The room page calls Magic's table endpoint for every room type,
  and it 404s for bomberman (prod log, room r-e15c835b31c6 at 18:28:56Z; the relay joined fine).
- **1b:** the game area is squashed.
- **1c:** bomberman's "add bots" button sits inside the game when it should be the room's seats.

The operator's direction (2026-11-16, settled below): **no bomberman code in cardtable**. The bomberman experience lives
at `hadoku.me/bomberman`, built in bomberman's repo on cardtable's published packages. Rooms work the same way on every
site. This wave is stage 1, which builds what bomberman and watchparty will import. Stage 2 (bomberman's repo) and
stage 3 (watchparty embeds) come after it lands.

The survey this brief is built from is `~/.cache/cardtable-manager/bomberman-survey-2026-11-16.md`; read it first.

## Size — checked before dispatch

4 lanes, each over an hour, across two repos:
- **P** is watchparty's `rooms-protocol` seat operations;
- **S** rebuilds cardtable's server seats on them;
- **C** makes game-server's config generic;
- **U** builds the UI pieces, makes the room page generic and removes bomberman.

P and S are ordered (S consumes P's publish). C, S and U own disjoint files. S is the long pole, so dispatch P and S
at t=0: S does its record migration and generic room socket first, and takes P's package when it publishes.

## Settled — do not re-open in any lane

- **No bomberman code in cardtable** (operator, 2026-11-16).
  - Cardtable may still create a bomberman room behind an experimental flag. That has to be **configuration, not
    code**: a generic "external game" room type with one flag-gated config entry naming the type id, label, seat
    range, runtime `relay`, its embed URL and its seat-rejoin grace.
  - Deleting that one entry removes bomberman from cardtable.
- **Every member of every room is either a player (seated) or a spectator, never neither** (operator, 2026-11-16).
  - Anyone removed from a seat becomes a spectator, whatever the path: they stand, the leader removes them, the seat
    count is lowered under them, or a bot replaces them.
  - One shared implementation; each site deletes its copy.
- **Three layers** (operator, 2026-11-16):
  - **L1, being in a room** (join, leave, members, leader, presence, chat): `@wolffm/rooms-protocol` +
    `@wolffm/rooms-server`, shared by all three sites.
  - **L2, seats** (opt-in per room): `rooms-protocol`'s `seats.ts`, the one implementation. Cardtable's
    `game-server` rebuilds its `GameSeats` on it and deletes its own copy. A plain watchparty room never turns seats on.
  - **L3, seat UI:**
    - **L3a**, shared pieces in `@hadoku/game-ui`: a seat-state hook, the seat chip (face, name, empty or bot), the
      sit/stand/remove controls, the spectator row.
    - **L3b**, each game's own lineup, composed from those pieces. Cardtable keeps its in-page lineup; bomberman
      builds an overlay lineup in its own repo. The operator expects the two to differ.
- **Bots are room seats.** The leader adds a bot from the seat lineup; the game running in the room host's tab plays
  it, as bomberman's bots work today.
- **The front page is a reusable module.** Room create plus room list, with optional slots for the banner, nav tools
  and featured cards; a slot with no content renders nothing. Bomberman's front page will be this module with no
  banner.
- The usual rules:
  - no version edits in cardtable, and none in watchparty either (its CI versions);
  - no AI attribution;
  - never `git stash`;
  - never `pnpm install` in a cardtable worktree;
  - never `/cutrelease` or `release.yml`;
  - never write under `~/srv` or `~/srv-data`;
  - e2e on claws only.

## §P — the seat operations, once (watchparty `rooms-protocol`)

`seats.ts` already derives role (`roleOf`: no seat means spectator) and has `unseatParticipant`. What no repo has is an
operation that removes a **seated** person: `padWithBots` and cardtable's `closeSeat`/`aiSeat` refuse an occupied
seat.

1. Add these, each leaving the removed person seatless (so `roleOf` says spectator) and their membership untouched:
   - remove a seated participant by the leader;
   - lower capacity under occupants (evict from the highest seat down, or a caller-chosen seat; document which);
   - replace a human with a bot.
   Pure functions, in the style of the file. Keep every existing export's signature.
2. Unit tests: for each operation, the evicted participant's `roleOf` is `'spectator'` and they are still a member,
   and no sequence of operations yields a member with no role. Mutation-test each op: remove the unseat step and the
   test goes red.
3. Land on watchparty main through its own gate; confirm `publish-packages.yml` published and note the version.
4. Done when: the version is on the registry, and the closing note has the new exports and their test counts.
